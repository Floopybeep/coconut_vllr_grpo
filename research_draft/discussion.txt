● Huberization explained

  Problem with the current clamp

  The k3 KL estimator is kl(r) = exp(r) - r - 1 where r = log π_θ - log π_ref.
  It's nonnegative, zero only at r=0, convex.

  Current code does:
  r_clamped = r.clamp(-5, 5)
  kl = exp(r_clamped) - r_clamped - 1

  What this does to the loss surface (think of r as the variable, kl as the
  loss):

  kl(r)
    |        ___________   <- flat plateau at exp(5) - 5 - 1 ≈ 141
    |       /
    |      /
    |     /                <- rising, nonzero gradient
    |    /
    |  _/
    |_/_____________ r
   -5      0       5

  Outside [-5, 5]: loss is constant, gradient is exactly zero (because clamp's
  derivative is 0 there, and r_clamped is the only path to r). So a token at
  r=10 is treated identically to a token at r=5: same constant penalty, no force
   pulling it back. The further it drifts, the more "free" it is.

  What Huber-style means

  In robust regression, the Huber loss is quadratic near 0, linear in the tails:
  H(x) = 0.5 * x^2          if |x| <= δ
  H(x) = δ * (|x| - 0.5*δ)  if |x| > δ
  It's continuous, monotone, gradient nonzero in the tails (constant ±δ). You
  get bounded gradient (good for stability) without flatlining.

  Applied to k3 KL: keep exp(r) - r - 1 near zero, switch to a linear extension
  once |r| > δ. The linear piece is matched to the k3 value and slope at ±δ so
  the function stays continuous and C¹.

  Concrete formula

  For threshold δ = 5:

  kl(r) = exp(r) - r - 1                                  if |r| <= δ   (k3,
  unchanged)
  kl(r) = (exp(δ) - 1) * (r - δ) + (exp(δ) - δ - 1)        if r > δ    (linear
  extension)
  kl(r) = (exp(-δ) - 1) * (r + δ) + (exp(-δ) + δ - 1)      if r < -δ

  Slopes:
  - Inside: d(kl)/dr = exp(r) - 1. At r = δ, slope = exp(δ) - 1 ≈ 147.
  - Outside (positive side): constant exp(δ) - 1 ≈ 147.
  - Outside (negative side): constant exp(-δ) - 1 ≈ -0.993.

  Properties:
  - Continuous and differentiable at ±δ (slope-matched linear pieces).
  - Gradient never zero for r ≠ 0 — drifted tokens still feel a pull toward
  π_ref.
  - Gradient bounded by |exp(δ) - 1| on the positive side — no exp explosion in
  bf16.
  - Identical to k3 inside [-δ, δ] so behavior under normal operation is
  unchanged.

  The asymmetry (slope ~147 above, ~1 below) is intentional and matches the
  asymmetry of k3 itself: KL penalizes "policy too confident on something ref
  isn't" much harder than the reverse.

  Implementation note

  In PyTorch we just gate with torch.where on the raw r:

  r = mb_new_lp - mb_ref_lp
  delta = 5.0
  e_pos = math.exp(delta)
  e_neg = math.exp(-delta)

  kl_inside  = torch.exp(r) - r - 1.0
  kl_pos     = (e_pos - 1.0) * (r - delta) + (e_pos - delta - 1.0)
  kl_neg     = (e_neg - 1.0) * (r + delta) + (e_neg + delta - 1.0)

  mb_kl = torch.where(r > delta, kl_pos,
          torch.where(r < -delta, kl_neg, kl_inside))

  torch.where passes gradient through the selected branch; no clamp on the
  input. The exp(r) inside kl_inside is only evaluated where |r| <= 5, so values
   are bounded ≤ exp(5).

● It works in principle but has structural inefficiencies that make it worse
  than alternatives. Let me lay out what each approach actually buys:

  What you'd be doing with per-batch skipping

  For each batch:
    1. Roll out K rollouts per prompt (expensive, ~70% of step time)
    2. Compute batch accuracy
    3. If accuracy in [low, high]: do policy update
       Else: discard, fetch next batch

  The rollouts are already done by the time you decide to skip. You only save
  the policy-update cost (theta_old replay + ref replay + backward), maybe 30%
  of step time. So a 50% skip rate gives you ~15% throughput recovery, not 50%.

  Three structural problems

  1. Coarser than DAPO already gives you. DAPO masking filters at the group
  level (per unique prompt's K rollouts). Per-batch skip filters at the batch
  level. If a batch has 16 prompts and 8 are all-correct + 8 are productive,
  batch accuracy ≈ 0.75 — wouldn't trigger most reasonable thresholds. You'd
  skip very few batches but DAPO would still rescue you on the same batch.
  2. DDP sync. All ranks must take the same number of optimizer steps. If rank 0
   sees a "good" batch and rank 1 sees a "skip" batch, they hang or desync
  gradients. Fixable with an all_reduce on the skip decision, but the slowest
  rank's accuracy controls everyone.
  3. Doesn't save the expensive part. The whole point of avoiding uninformative
  samples is to not waste rollout compute on them. Per-batch skip wastes the
  rollouts and only saves the cheap downstream parts.

  Better cuts of the same idea

  If the goal is "skip useless work without writing a separate screening pass,"
  the higher-leverage version is per-prompt filtering in the dataloader:

  Maintain: live_pool (productive prompts), dead_pool (mastered or unsolvable)
  Each step: sample from live_pool only — no rollouts wasted on dead prompts
  After each batch: update each rolled-out prompt's status from observed
  accuracy
  Every N steps: retest a sample from dead_pool to catch promotions/demotions

  This saves rollout cost (the actual bottleneck), adapts continuously without a
   separate pass, and is finer-grained than per-batch.

❯ Why shouldn't we skip advantage/policy calculation if no groups pass the      
  filter?                                                                       

● Honestly — you're right that skipping is more semantically correct. The
  fallback was defensive, not principled. Here's the trade-off:

  Why fallback is wrong in spirit

  The filter exists precisely because zero-signal groups produce bad updates.
  When 0 groups pass, falling back to "use all of them anyway" means:
  - Advantages are all ≈ 0 (zero variance → 0/σ_r → 0).
  - Policy loss → 0, no useful gradient.
  - KL term still ≠ 0 (policy still differs from ref).
  - Net update = pure KL pull toward ref, with no reward signal to balance it.

  That's strictly worse than doing nothing. The fallback is producing exactly
  the "drag back toward ref" dynamic we tuned kl_beta to avoid. Skipping is the
  correct behavior.

  Why I implemented fallback anyway

  Three engineering reasons, in decreasing weight:

  1. DDP gradient sync. PyTorch DDP expects every rank to call loss.backward()
  in lockstep — it uses the backward pass to all-reduce gradients across ranks.
  If rank 0 skips and rank 1 doesn't, rank 1 hangs forever waiting for rank 0's
  gradient bucket. So "skip" can't be a per-rank decision; it has to be a global
   one (every rank either skips or not).
  2. Scheduler / step counter consistency. lr_scheduler.step() and
  optimizer.step() are paired. Skipping optimizer.step() while still calling
  lr_scheduler.step() desyncs them; doing neither freezes the schedule. Either
  is recoverable but needs explicit handling.
  3. Edge case rarity. With sensible bounds (≤ 0.85 upper), 0 groups passing
  across an entire 16-prompt batch is rare unless the dataset is wildly
  polarized. The fallback's "wrong" behavior almost never actually fires.

  How to implement skip cleanly

  The DDP issue forces an all-reduce on the decision:

  n_kept_local = torch.tensor(n_kept, device=device, dtype=torch.long)
  dist.all_reduce(n_kept_local, op=dist.ReduceOp.SUM)
  n_kept_global = n_kept_local.item()

  if n_kept_global == 0:
      # All ranks skip together: no optimizer.step, no lr_scheduler.step,
      # no theta_old/ref replay. Log diagnostics and move on.
      skip_step = True

  Then wrap the theta_old replay / ref replay / policy update / optimizer.step /
   lr_scheduler.step block in if not skip_step:. The pbar still advances (so we
  don't get stuck), wandb still logs (with train/loss = 0, filter_kept_frac = 0,
